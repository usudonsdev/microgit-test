# ビルド検証エンジン 設計レビュー（実装突き合わせ）

作成: 2026-09-12
対象: [build-verification-engine.md](./build-verification-engine.md)（計画段階）
方法: 設計書の前提を `src/extension.ts` / `src/overlay.ts` / `src/shadowStore.ts` の現行実装と突き合わせ

> このメモは設計書を置き換えない。**設計書の記述のうち、実装と食い違う前提・論理の弱い主張**を列挙し、
> 解消方針を提案する。採否を決めたら設計書本体（ADR / §15）へ反映し、本メモに「反映済み」と追記する。

## 0. 結論（先に）

設計の骨格（ADR-001〜010）は概ね妥当。ただし**最上流の前提が1つ崩れている**。

> エンジンは `views/<hash>/` をコンパイル対象にする（設計書 §5.1, §14）。
> しかし現行の `views/<hash>/` は**コンパイル可能なプロジェクトではない**。

これが解決するまで F-01（保存時のビルド可否判定）は実装できず、
したがって新規性A・B の測定（E-01〜E-03）もすべて着手できない。
§15 のクリティカルパス①（reflink）より**さらに上流**にこの項目を置く必要がある。

重大度: R-01〜R-03 が設計変更を要する。R-04〜R-07 は主張・測定設計の修正。R-08〜R-10 は補強。

## R-01【致命】`views/<hash>/` は部分ツリーであり、コンパイルできない

### 実装の実際

- `ensureShadowRepoForBranch`（`shadowStore.ts:66`）は `git init --bare` で**空のリポジトリ**から始める。既存ワークスペースのシードは行わない
- `runShadowCommit`（`extension.ts:982`）は保存された**1ファイルだけ**をシャドウ作業ツリーへ書き、`git add -- <その1ファイル>` してから `write-tree` する
- 結果として、シャドウの tree に存在するのは「MicroGit 有効化後に一度でも保存されたファイル」だけ
- `views/<hash>/` は親ビュー + 差分レイヤの合成（`overlay.ts:209 ensureExpandedView`）なので、当然その部分集合を引き継ぐ

### 何が起きるか

有効化直後に `src/a.ts` を1回保存した時点の `views/<hash>/` には `a.ts` しか無い。
`tsconfig.json` も `package.json` も他のソースも無い。`tsc --noEmit` は「入力が無い」か大量の解決エラーになる。
**赤/緑はソースの正しさではなく「まだ保存していないファイルの数」を測ることになる。**

### 対策の選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A-1 | 有効化時に `git ls-files` の全量をシャドウへシードし、以後は差分で伸ばす | 追加コストは初回のみ。現行の layer/view 構造をそのまま使える。**推奨** |
| A-2 | 未保存ファイルは検証時にワークスペース実体から補う（view + 現在のツリーの合成） | 「その時点の状態」ではなくなる。過去コミットの検証が意味を失う。却下 |
| A-3 | 検証対象を view ではなくワークスペース実体にする | 過去・他分岐の検証ができない。F-02/F-03 が消える。却下 |

A-1 は MicroGit 本体の仕様変更（`design-policy.md` §2 の記録単位）に触れる。
AGENTS.md の規定どおり **design-policy を先に更新**してからエンジン側を追随させる。

### 副次論点: 依存物（`node_modules` / `target/`）

A-1 で全量シードしても、`.gitignore` 対象の依存物はシャドウに入らない（入れるべきでもない）。
`tsc` を回すには `node_modules` が解決できる必要がある。設計書にこの項目が無い。

- 提案: `views/<hash>/` に `node_modules` を**固定実体への junction / symlink** で注入する。
  依存物はコミット単位で変わらない前提を置き、`package-lock.json` が変わったマイクロコミットでのみ再構築する
- この「依存物は別レイヤ」という切り分けは ADR-002 の「粒度の分離」と同じ発想であり、設計原則4 の適用範囲を
  「ソース = コミット単位 / ビルドキャッシュ = ブランチ単位 / 依存物 = ロックファイル単位」の三層へ拡張するのが素直

## R-02【重大】マイクロコミットは1ファイル単位。中間状態の赤が構造的に量産される

### 実装の実際

`runShadowCommit` は保存イベント1回 = 1ファイル = 1コミット。
契約 §7 の `changed_files: string[]` は、現行 MicroGit では**常に長さ1**になる。

### 何が起きるか

`A.ts` と `B.ts` を整合させる変更（インターフェース変更と呼び出し側の追従など）を保存すると、
片方だけ適用された中間コミットが必ず生成される。この中間コミットは**必ず赤**になる。

- Save All、AI による一括編集（`[AI]` 検知経路）では日常的に発生する
- 悉皆記録した赤の相当数が「本物の破壊」ではなく**保存順序の人工物**になる
- F-03（緑→赤の境目を原因コミットとする）は、この人工的な赤を原因として報告する

新規性B は「悉皆記録があれば原因特定が走査になる」という主張なので、
**記録された赤の意味が信用できないと主張ごと崩れる**。R-01 に次いで重い。

### 対策の選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| B-1 | 保存バースト（例: 300〜500ms 窓）内の複数ファイル保存を1マイクロコミットにまとめる | 記録単位そのものを変える。履歴の意味が「1ファイルの保存」から「1回の編集操作」へ移る。**推奨だが本体仕様変更** |
| B-2 | 記録は現状のまま、**検証単位だけ**バースト末尾に寄せる（途中は `unverified`） | 本体を変えない。ただし未記録区間が常態化し、F-07（区間二分探索）が主経路になる。ADR-007 の前提が弱る |
| B-3 | 中間コミットを「原子性が疑わしい」とマークし、F-03 の走査で緑→赤境界の候補からスキップする | 安いが、本物の赤も取りこぼす。ヒューリスティックであり ADR-009（推測を混ぜない）の方針と衝突 |

B-1 を採るなら、design-policy §2 の「記録単位 = 保存イベント」を
「記録単位 = 保存バースト」へ改める判断が要る。ユーザーから見た履歴の粒度が変わるので、
MicroGit 本体のプロダクト判断として先に決めること。

## R-03【重大】履歴は append-only の線形列ではない（HEAD の巻き戻しがある）

### 実装の実際

`runShadowCommit` は「以前と同じ変更（同一 tree / 同一ファイル内容）」を検出すると、
新規コミットを作らず `update-ref` で **HEAD を過去のコミットへ戻す**（`extension.ts` の `findPastCommitForSave` →
戻り値 `'rewound'`）。`mb-*` タグはブランチ先端にのみ付く。

### 何が起きるか

設計書 §6 の F-02 / F-03 は「成否列の後方走査」と書かれているが、
実際の対象は**時系列の列ではなく DAG 上の経路**。時刻順に並べた列を後方走査すると、
巻き戻しをまたいだ瞬間に親子関係のない2点を隣接として扱う。

### 対策

- F-02 / F-03 の定義を「時系列の後方走査」から「**現在の tip から親リンクを辿る経路の走査**」へ書き換える
- 経路は `.microgit_overlay/meta/dag.json`（`overlay.ts:70`）が既に持っている。新規に持つ必要はない
- 「同じ状態へ戻った」＝**同じコミットID＝検証結果も同一**なので、巻き戻しはむしろ
  「検証をスキップしてよい」ことの根拠になる（キャッシュヒット）。設計書に利点として書ける

## R-04【重大】E-01 のベースライン比較が現行実装では差を示さない

### 実装の実際

設計書 §2.1 は `git worktree` + フルビルドの欠点として「作業ツリーのフル書き出し」を挙げる。
しかし `ensureExpandedView` / `expandViewAfterExport` は親ビューから `copyTreeBytes`
（`overlay.ts:254`, `overlay.ts:291`）、すなわち**保存のたびにソースツリー全体のバイトコピー**を行う。
コード内コメントも「view 構築は実体コピー（ハードリンクは小ファイル多数で逆に遅いことがある）」と明記。

つまり **ソースの materialize コストでは `git worktree` と原理的に差がつかない**。
差が出るのはビルドキャッシュ側だけ。

### 対策

- E-01 を「合計時間の比較」ではなく、**「ソース展開」と「ビルド」の内訳を分けて測る**設計に変える。
  主張は「ビルドキャッシュの再利用で後者が消える」であって、前者ではない
- 同時に、views 側の展開コストを下げる余地があるなら別課題として切る（reflink があればここにも効く）。
  ただしこれは MicroGit 本体の最適化であり、エンジンの新規性主張とは別勘定にする

### 付随: views/ に GC が無い

`src/` 内に views / layers の保持世代制御・削除経路は存在しない（`rmSync` は merge ディレクトリと
checkout 経路のみ）。1日数百コミット × フルツリーのバイトコピーが無制限に積み上がる。

ADR-002 は「コミット単位でキャッシュを持つとメタデータと GC が破綻する」を却下理由にしているが、
**ソース側では既にその破綻を抱えている**。ADR-002 の論理を維持するなら、
「ソースは1コミットあたり数MB、ビルドキャッシュは数百MB〜GB で3桁違う」という**サイズ差**を根拠にすべきで、
「コミット数が多いから」だけを根拠にすると自分の実装と矛盾する。§13 に views の GC ポリシーを追加すること。

## R-05【重大】Windows では CoW 前提が成立しない。M0 は「スパイク」ではなく「方針決定」

### 事実関係

- NTFS に reflink 相当の機能は無い。Windows のブロッククローンは **ReFS（Dev Drive 含む）** の機能
- `containerd/snapshots` の overlayfs / btrfs / zfs バックエンドは Linux 前提。
  windows snapshotter は Windows コンテナのイメージレイヤ用であり、開発機上の任意ディレクトリを
  CoW 複製する用途には使えない
- 開発環境は Windows 11（本リポジトリの動作環境）

### 何が起きるか

§15 の M0「Windows(NTFS) での reflink 実現可否スパイク（1日）」は、調べる前から結論がほぼ出ている。
1日かけて「できない」を確認する作業になる。そのうえで ADR-004（containerd 採用）は
**暗黙に Linux を主環境と仮定している**が、設計書のどこにもそれが書かれていない。

### 対策

M0 を「可否の調査」から「**主評価環境の決定**」へ置き換える。選択肢:

| 案 | 内容 | 評価 |
|---|---|---|
| C-1 | 研究の主評価環境を Linux（btrfs / XFS reflink）とし、Windows はフルコピーへのフォールバックとして扱う | containerd をそのまま使える。ADR-004 が生きる。**推奨** |
| C-2 | Windows + Dev Drive(ReFS) を主環境にする | 開発機と一致するが、containerd snapshotter が使えず CoW 層を自前で書くことになる。ADR-004 の却下理由（維持コスト）が自分に返ってくる |
| C-3 | CoW を諦め、ハードリンク + 「書き込み前にコピー」を自前実装 | §12 の「hardlink による破壊」リスクを正面から抱える。ビルドツールの in-place 書き換えを完全に捕捉できないので却下 |

C-1 を採る場合、ADR-004 に「本設計は reflink 相当を持つ FS を前提とする。前提を満たさない環境（NTFS）では
フルコピーへ退避し、性能主張の対象外とする」を明記する。これは**適用限界の明示**であって弱点ではない。

## R-06【中】ADR-006「偽の赤はほぼ起きない」は ADR-002/003 と衝突している

ADR-006 は「本当は正しいのに赤、はほぼ起きない」を非対称性の根拠にしている。
しかし ADR-002（キャッシュを複製して別パスで再利用）と §12（絶対パスの埋め込み）を併せると、
**複製したキャッシュの不整合が偽の赤を生む経路が設計の中に存在する**。
「赤は信頼」を無条件に置くと、この経路が原因特定の結果を汚染する。

### 対策

赤を確定させる手続きを1段入れる。

> 検証が赤になったコミットは、キャッシュを使わずに1回だけ再検証して確定する（クリーン再実行）。
> 2回目も赤なら確定赤、緑なら「キャッシュ起因の偽陽性」として記録し、当該ブランチのキャッシュを破棄する。

- コストは**赤のときだけ**発生する。緑が大多数である以上、悉皆記録の速度前提を壊さない
- ADR-005 の「未検証フラグ → 次回強制フルリビルド」と同じ考え方の適用先違いであり、設計として一貫する
- 副産物として「キャッシュ起因の偽陽性率」が測定できる。これは ADR-002 の妥当性を支える実測値になり、
  評価計画に E-05 として追加する価値がある

## R-07【中】E-02 の測定定義が曖昧で、ADR-002 の本命を測っていない

現行の記述は「分岐頻度を上げたとき、キャッシュ複製コストが利得を上回る点」。
これは **fork が安いこと**しか測らない。しかし ADR-002 が単一キャッシュ方式を却下した理由は
「ブランチ間を往復すると交互に上書きされて効きが悪くなる」であり、**そちらが本命**。

### 対策: E-02 を2つに分ける

| ID | 独立変数 | 従属変数 | 比較対象 |
|---|---|---|---|
| E-02a | 分岐回数 | 複製にかかる総時間・ディスク使用量 | `cache/mb-N`（reflink） vs 素朴コピー vs キャッシュ無し |
| E-02b | **ブランチ往復頻度**（分岐間の切替回数） | 検証1回あたりの所要時間 | `cache/mb-N` vs 全ブランチ共通の単一キャッシュ（BuildKit / ccache 方式） |

E-02b が ADR-002 の却下理由を直接支える測定であり、新規性A の主張に最も近い。
現行の §11 には対応する項目が無いので追加すること。

## R-08【中】F-04（原因位置の単語単位特定）は交差が空のとき答えられない

「原因コミットの差分 ∩ コンパイラの span」は、交差が空になるケース（型定義の変更が遠方でエラーを起こす）が
実際には少なくない。ADR-009 はそれを認めて LLM 送りにしているが、
そうすると **F-04 は「重なるときだけ答えられる機能」**になり、研究の貢献としては弱い。

### 対策

交差が空のときの決定的フォールバックを定義する。いずれもコンパイラの構造化出力から得られ、推測を含まない。

1. 診断の `relatedInformation`（tsc の「関連情報」/ cargo の note・help スパン）が指す位置を第2候補とする
2. 同一エラー（R-09 の同一性キー）が**そのブランチで初出したコミット**の差分を原因位置とする
3. 1・2 とも空なら「原因位置は特定不能、原因コミットのみ確定」と明示的に返す（推測で埋めない）

「答えられない場合を確定的に切り分ける」ことは ADR-009 の方針と整合し、むしろ主張を強くする。

## R-09【小】エラー同一性キーにファイルパスと診断カテゴリを加える

§6.2 は「code + message + シンボル名」。これだと、同一エラーが**別ファイルで**起きた場合に同一視される。
`file` の相対パスと診断の重大度（error / warning）を含めた複合キーにする。
リネーム追従は当面スコープ外と明記しておけば、限界の明示として足りる。

## R-10【小】研究テーマ「mergeless branching」との接続が設計書に書かれていない

新規性A・B はどちらも、読む限り **mergeless でなくても成立する**（通常の git でも悉皆記録すれば走査になる）。
卒論のテーマが mergeless branching なら、両者の依存関係を明示しないとテーマと実装がつながらない。

### 使える根拠は既に手元にある

`design-policy.md` §4.1 に、MicroGit のマイクロコミットは
**`commit-tree -p <parent>` により常に単一親のみを持つ（意図的な不変条件）** と記録されている。

これは本設計にとって強い前提になる:

- 合流点が存在しない ⇒ 任意のコミットから根までの**経路が一意に定まる**
- したがって「緑→赤の境目」が一意に定義でき、F-03 は経路上の単純走査で閉じる
- マージコミットがある通常の git では、赤の原因が「どちらの親から来たか」の判定を伴い、
  走査は木の探索になる（`git bisect` が merge を特別扱いするのと同じ事情）

**つまり「mergeless だから走査で済む」が言える。** 現行の設計書はこの最も強い根拠を使っていない。
§10.2 の新規性B に、この依存関係を明記すること。

## 11. 提案する順序の修正

§15 のマイルストーンに対し、**M0 より上流に2件**を差し込む。

| # | 内容 | 理由 | 見積り |
|---|---|---|---|
| **M-2** | R-01 の解決: シャドウ全量シード（A-1）+ 依存物の注入方式を決め、`views/<hash>/` で `tsc --noEmit` が通ることを実証 | これが通らないと F-01 が存在し得ない。最上流 | 3〜5日 |
| **M-1** | R-02 の方針決定: 記録単位を保存バーストにまとめるか（B-1）、検証単位だけ分離するか（B-2）。design-policy §2 を先に更新 | 悉皆記録された赤の意味が決まる。新規性B の土台 | 判断1日 + 実装3日 |
| M0' | R-05: 主評価環境の決定（C-1 推奨）。「NTFS で reflink できるか」ではなく「どこで測るか」を決める | 結論はほぼ出ている。調査ではなく決定 | 0.5日 |

そのうえで既存の M1（複製後の再利用性）以降へ進む。
M3（containerd 組み込みスパイク）は**クリティカルパスから外して後ろに回す**ことを推奨する。
E-01〜E-03 の測定自体は reflink コピーの薄いラッパと計測ハーネスがあれば成立し、
containerd 採用は「実装可能性の裏付け」として後から足せるため。
卒論スコープで Go デーモン + containerd + Windows 名前付きパイプを全部クリティカルパスに載せるのはリスクが高い。

## 13. ここからどう設計を詰めるか

### 13.1 診断: 設計書が「詰まっていない場所」と「詰め過ぎている場所」がずれている

現行の設計書は、**証拠が無い領域ほど詳しく書かれ、決定が必要な領域ほど書かれていない**。

| 領域 | 現状 | 実際に必要なこと |
|---|---|---|
| 実装手段（Go / containerd / 名前付きパイプ / §7 契約） | ADR-004、§4、§7 で詳細に確定済み | **まだ確定できない**。上流の測定結果で要否が変わる |
| 検証対象ツリーの構成（何をコンパイルするか） | §5.1 に `views/<hash>` と1行 | **最も決めるべき箇所**。R-01 により現状は成立しない |
| 記録単位（1コミットの意味） | design-policy §2 から暗黙に継承 | **プロダクト判断が必要**。R-02 により赤の意味が変わる |
| 新規性の定量的裏付け | 「E-02 が最重要」と書いてあるが未実施 | 最も安く測れるのに最後に置かれている |

したがって次にやるべきは **ADR を増やすことではない**。
リスクの高い仮定を「1日で潰せる実験」に変換し、**測定結果に ADR を書かせる**。

### 13.2 重要な事実: 最重要の測定に Go も containerd も要らない

新規性A・B を支える測定（E-01、E-02a/b、E-03）は、いずれも
**ディレクトリ操作とビルドコマンドの計測**でしかない。常駐デーモンも CoW ライブラリも不要。

現行の §15 は M3（containerd 組み込み）と M4（通信層）をクリティカルパスに置き、
測定（M6）をその後ろに置いている。**順序が逆**。
測定が先に否定的な結果を出した場合、M3・M4 の実装は丸ごと無駄になる。

### 13.3 フェーズ0: 先に回す3つのスパイク（各1日・実装ほぼ不要）

いずれも失敗したときに**設計のどこが変わるか**が確定しているものだけを選ぶ。

| ID | 内容 | 得られる値 | 失敗時に変わるもの |
|---|---|---|---|
| S-1 | `views/<hash>/` に全量シード + `node_modules` を junction し、`tsc --noEmit` が通るか | view 展開時間 / tsc 時間の内訳（E-01 の分解値） | R-01 の A-1 が破綻。検証対象の構成から再設計 |

| S-3 | 分岐別キャッシュ vs 全ブランチ共通の単一キャッシュを、**ブランチ往復**しながら比較（E-02b の予備） | 往復頻度ごとの1回あたり検証時間 | **差が出なければ新規性A が消える**。卒論の軸が新規性B のみになる |

かつ**ディレクトリ2つを交互にビルドするだけ**で測れる。
卒論の軸を左右する判断が、いちばん安い作業で得られる。これを最後に回してはいけない。

S-2 の失敗は見落としやすい重要な帰結を持つ。固定パスマウントが必須なら、
「複数の分岐を同時に検証する」ことがパス衝突で不可能になり、
検証はシリアル化される。F-07（未記録区間の二分探索）の頻度が上がる方向に効く。

### 13.7 退避ルート: 新規性A が消えた場合の卒論

S-3 で分岐別キャッシュの優位が出なかった場合、新規性A は主張できない。

- 主張: 単一親不変条件（mergeless）+ 悉皆記録 ⇒ 原因特定が一意な経路の走査になる（R-10）
- 必要な実装: 検証結果の記録と経路走査。**CoW も Go も containerd も不要**。TypeScript で MicroGit 内に収まる
- 評価: E-01（既存手段との比較）、E-03（走査 vs 二分探索）、E-05（偽陽性率）
- 失うもの: E-02。「保存のたびの検証が現実的な速度で回る」の裏付けが弱くなるため、
  検証頻度を落とした場合（F-07 が主経路になる場合）の性能を代わりに示す必要がある

この退避ルートが**先に存在を確認できている**ことが重要。
S-3 の結果が出る前に Go デーモンの実装に着手すると、この選択肢を取るコストが跳ね上がる。

## 14. 【未決・要判断】MicroGit と同一のソフトとしてやる必要があるか

### 14.1 問いの整理: 「分けるか」ではなく「卒論の主語はどちらか」

ADR-008 は既に「エンジンを MicroGit から分離する」と決めているが、それはプロセス分離の話であり、
**研究として同じものを扱うのか**は別問題。実際には4つの軸があり、混ざっている。

| 軸 | 現状の決定 |
|---|---|
| 同一プロセスか | 別プロセス（ADR-008）。決定済み |
| 同一リポジトリか | 未決 |
| 同一プロダクトか（MicroGit の機能として出すか） | 未決 |
| **研究の入力が MicroGit に依存するか** | §14 で `views/` に直結。ADR-008 の「任意の VCS から利用可」と矛盾 |

### 14.2 新規性A と B は、MicroGit への依存度が正反対

これが問いの核心。

| | 新規性A（CoW キャッシュの分岐追従） | 新規性B（探索 → 走査） |
|---|---|---|
| mergeless との関係 | **無関係**。通常の git でも成立する | **依存する**。単一親だから根までの経路が一意（R-10） |
| MicroGit の必要性 | 不要。高頻度スナップショットさえあればよい | MicroGit の不変条件そのものが根拠 |
| 必要な実装 | Go + containerd + reflink + Linux | 検証結果の記録と経路走査のみ。TypeScript で足りる |
| 主張が崩れるリスク | S-3 次第。BuildKit の再実装に後退する可能性（§15.1 に自記） | 低い。記録さえ信用できれば論理で閉じる |

設計書は「研究テーマ mergeless branching の一事例」と宣言しながら、
記述量の大半を **mergeless と無関係な新規性A** に割いている。
「同じソフトでやるのか」が決まらないのは、この**テーマと重心のずれ**が原因。

### 14.3 3つの構成案

| 案 | 卒論の主語 | MicroGit の位置 | 実装 | 評価 |
|---|---|---|---|---|
| **P-1** | mergeless branching（新規性B が中核） | **主題そのもの**。エンジンは MicroGit の一機能 | TypeScript のみ。Go/containerd/Linux 不要 | 宣言テーマと一致。最短。S-3 が失敗しても生き残る。**推奨** |
| P-2 | ビルドキャッシュの CoW 分岐追従（新規性A が中核） | 単なる入力源。切り離してよい | Go + containerd + Linux 必須 | システム寄りで見栄えはするが、mergeless テーマと接続しない。S-3 に全賭け |
| P-3 | 両方（現行の設計書） | 入力源かつ主題 | 全部 | 卒論スコープでは重い。かつ R-01〜R-03 の本体改修が研究外の工数として乗る |

### 14.4 R-01〜R-03 は「結合が間違っている」というシグナル

レビューで見つかった不整合は独立に3つある。

- R-01: ツリーが部分的でコンパイルできない
- R-02: 1ファイル1コミットで人工的な赤が出る
- R-03: HEAD が巻き戻り、列が線形でない

いずれも「MicroGit の記録モデルがビルド検証に向いていない」ことの現れ。
3つ独立に出るということは、**個別に直す問題ではなく結合の設計が間違っている**可能性が高い。

とくに R-02 の対策 B-1（記録単位を保存バーストへ変更）は、
**公開済みプロダクトのユーザーから見える履歴の粒度を、卒論の実験のために変える**ことを意味する。
これは順序が逆。MicroGit 側の変更は「MicroGit にとって正しいか」で判断すべきで、
研究の都合を理由にしてはいけない。

### 14.5 どの案を採っても成立する分離線: 評価入力を MicroGit から切る

**構成案の選択と独立に、これは採用してよい。**

研究の測定（E-01〜E-03）の入力を、MicroGit 直結ではなく
**再生可能な「編集列（トレース）」形式**にする。

- MicroGit はそのトレースを生成する **adapter の1つ**。唯一の入力源にしない
- 合成ワークロード、OSS リポジトリのコミット列も同じ形式へ変換できる
- 利点:
  1. **再現性**。「自分の VS Code で使った」より、記録した編集列を再生するほうが卒論の証拠として強い。審査側が追試できる
  2. **日程**。R-01/R-02 の本体改修完了を待たずに S-1〜S-3 を回せる
  3. ADR-008 が主張する「任意の VCS / 監視ツールから利用可能」が、実際に検証された主張になる
     （現行 §14 は `views/` 直結なので、この主張は今のところ**未検証の願望**）

### 14.6 現時点の推奨

**P-1**（mergeless を主語、新規性B を中核）+ §14.5 の分離線。

理由:

- 宣言済みのテーマと実装の重心が一致する。§10.2 に書くべき根拠（単一親不変条件）は既に手元にある（R-10）
- Go / containerd / Linux / 名前付きパイプがまるごとクリティカルパスから外れる。卒論スコープに収まる
- S-3 の結果に依存しない。新規性A は「補助的な最適化」として、測れたら加える位置づけにできる
- MicroGit 本体の改修（R-01 の全量シード）は P-1 でも必要だが、**R-02 の記録単位変更は必須でなくなる**
  （検証単位だけ分離する B-2 で足りる。プロダクトの見え方を変えずに済む）

P-2 を採るなら、MicroGit とは**別リポジトリ・別プロダクト**として切り出し、
卒論のテーマ宣言も「mergeless branching」から書き換える必要がある。中途半端な結合がいちばん悪い。

### 14.7 この判断を先にすべき理由

§13 のフェーズ0（S-1〜S-3）のうち、**S-2・S-3 は P-2 を採る場合にしか必要ない**。
P-1 なら CoW キャッシュ自体が中核から外れるため、優先度が大きく下がる。

したがって **14.3 の構成案の選択が、§13 の手順より上流**にある。ここを先に決めること。

## 15. 【決定 2026-09-12】構成案 P-2 を採用（主軸はビルド検証エンジン）

§14.3 の選択肢のうち **P-2** を採る。エンジンが卒論の主語であり、MicroGit は入力源の1つ。

この決定により、以下が確定・変更される。

### 15.1 確定すること

| 項目 | 決定 |
|---|---|
| 卒論の主語 | ビルド検証エンジン。「mergeless branching の一事例」という位置づけ宣言は書き換える |
| MicroGit の位置 | 入力トレースを供給する **adapter の1つ**。唯一の入力源にしない |
| リポジトリ | 別リポジトリへ切り出す。本リポジトリには adapter 実装のみ残す |
| 主評価環境 | **Linux（reflink 可能な FS）を必須前提とする**（R-05 の C-1）。P-1 なら任意だったが P-2 では必須 |
| S-2 / S-3 | **クリティカルパス上**。P-1 では優先度が下がるはずだったが、P-2 では新規性A が中核なので必須 |

### 15.2 最大の帰結: §7 の契約にソースツリーを取得する手段が無い

現行契約の入力は `branch_id` / `parent_branch_id` / `commit_id` / `changed_files` のみ。
**これは変更されたファイル「名」であって、中身でもツリーでもない。エンジンはこれをコンパイルできない。**

MicroGit と結合していた間は、この穴が `views/<hash>` への直接参照（§14）で塞がれていた。
分離した瞬間に穴が露出する。**契約の再設計が P-2 の最初の作業になる。**

#### ツリー取得方式の選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| T-1 | adapter が「そのコミット時点の完全ツリーがあるディレクトリのパス」を渡す | 実装は軽いが、パスを adapter が決めるため **エンジンがパスを固定できない**。S-2（`.tsbuildinfo` の絶対パス問題）の対策と衝突する。却下 |
| T-2 | adapter は **git 互換のオブジェクト供給源（bare repo のパス）+ commit_id** だけを渡し、**エンジンが自分の管理下へ展開する** | エンジンが展開先パスを完全に制御できる ⇒ 固定パス運用が可能になり S-2 の対策が成立。ツリーの完全性もエンジン側で検証できる（R-01 が adapter のバグとして検出可能になる）。**推奨** |
| T-3 | adapter がファイル内容をストリームで渡す | プロトコルが重く、大きなツリーで非現実的。却下 |

T-2 を採ると、契約はおおよそ次の形になる（命名確定後に凍結）。

```
入力:
  object_source : string   // bare git repo のパス（オブジェクトの供給源）
  commit_id     : string
  parent_id     : string | null
  lane_id       : string   // 分岐の識別子（キャッシュの帰属先。MicroGit の mb-* に相当）
  parent_lane_id: string | null
  changed_files : string[] // 任意。最適化のヒントであり、正しさの根拠にしない
出力:
  status, errors[]   // 現行 §7 のまま
```

- `changed_files` を**ヒントに格下げ**する点が重要。ADR-001（差分判断はコンパイラに委譲）と整合し、
  R-02（1ファイル1コミット）が契約レベルの問題ではなくなる
- `branch_id` を `lane_id` に改名する案: 「git の branch」と「キャッシュの帰属先」は別概念であり、
  同名にすると adapter 実装者が混乱する。エンジンにとっては「キャッシュを共有する一本の列」でしかない

### 15.3 評価データが一気に強くなる（P-2 採用の最大の利点）

T-2 を採ると **入力が「git リポジトリ + コミットID の列」になる**。つまり:

> **任意の OSS リポジトリが、そのまま評価データセットになる。**

- 実際のコミット列を再生して E-01〜E-03 を測れる。審査側が追試できる
- 実際に壊れたコミットが含まれるため、F-03（原因コミット特定）の**正解データが手に入る**
- MicroGit の実装改修（R-01）の完了を待たずに測定を開始できる

**ただし限界も明記すること**: OSS のコミット列は保存粒度ではない。
「高頻度スナップショットが既に存在する」という前提（§2.2）を実証するには、
保存粒度のトレースが別途要る。したがってトレース源は2種類を使い分ける。

| トレース源 | 役割 |
|---|---|
| OSS リポジトリのコミット列 | 規模・再現性・原因特定の正解データ。E-01 / E-02 / E-03 の主測定 |
| MicroGit（保存粒度） | 「保存のたびの検証が現実的か」という前提の実証。E-04 と適用限界 |

### 15.4 新規性B の根拠が MicroGit から切れる問題と、その解決

R-10 は「単一親不変条件（mergeless）⇒ 経路が一意 ⇒ 走査で閉じる」を新規性B の根拠とした。
しかし P-2 で MicroGit を主題から外すと、この根拠は**他人の性質**になってしまう。
さらに OSS リポジトリにはマージコミットがあり、単一親が成り立たない。

#### 解決: エンジン自身が履歴モデルを宣言する

単一親性を「MicroGit がそうだから」ではなく、**エンジンの契約が要求する前提**として定義する。

> エンジンは入力を**単一親の列（lane）**として扱う。
> マージを含む履歴を入力する adapter は、あらかじめ線形化して渡す責任を負う。

- これで新規性B は MicroGit に依存しない主張になる
- OSS リポジトリは `git log --first-parent` で線形化すれば入力できる（adapter 側の責務として明記）
- 「合流点を持たない履歴だから原因特定が走査に退化する」という主張はそのまま生きる。
  mergeless は**テーマ宣言から前提条件へ格下げ**されるが、論理としては維持される

### 15.5 MicroGit 本体に残る作業（大幅に減る）

| 指摘 | P-2 での扱い |
|---|---|
| R-01（部分ツリー） | **必要**。ただし「MicroGit を保存粒度トレース源として使う」ための作業であり、測定開始をブロックしない（OSS トレースで先行できる） |
| R-02（1ファイル1コミット） | **本体改修が不要になる**。adapter 側で複数保存を1トレース項目に束ねればよい。`changed_files` がヒットに格下げされたため契約上も問題にならない。**プロダクトの見え方を変えずに済む** |
| R-03（HEAD 巻き戻し） | adapter が lane を線形化して渡す責務（§15.4）に吸収される |
| R-04（views の GC） | MicroGit 単体の課題として分離。研究とは別勘定 |

P-2 の副次的な利点として、**公開済みプロダクトの仕様を研究都合で変える必要がなくなる**（§14.4 の懸念が解消）。

### 15.6 改訂した手順

| 順 | 内容 | 備考 |
|---|---|---|
| 1 | **契約の再設計**（§15.2 の T-2）。ツリー取得手段を含む形に書き直す | 凍結はまだ。命名は後でよい |
| 2 | **S-3**（分岐別 vs 単一キャッシュ、ブランチ往復）を最優先で実施 | 新規性A が中核になった以上、ここが全体の可否を決める。Go も containerd も不要 |
| 3 | **S-2**（複製後のパス差異下での差分ビルド再利用） | T-2 の固定パス運用が効くかを同時に確認 |
| 4 | OSS リポジトリ1本を入力に、E-01 / E-03 の予備測定 | S-1（MicroGit 側）を待たずに走る |
| 5 | 測定が肯定的なら containerd 組み込み（旧 M3）、否定的なら §15.7 へ | |

S-1 は「MicroGit を入力源にするための作業」に格下げされ、クリティカルパスから外れる。

### 15.7 P-2 における退避ルート

S-3 で分岐別キャッシュの優位が出なかった場合、新規性A が崩れる。
P-1 と違い、P-2 では**これが主軸の崩壊**を意味するため、退避先を先に決めておく。

- 退避先: **新規性B 単独**（§15.4 により MicroGit 非依存で主張できる状態になっている）
- そのとき必要な実装は「検証結果の記録と経路走査」のみで、CoW も containerd も要らない
- つまり **§15.4 の作業（履歴モデルをエンジン側で宣言する）を先にやっておくことが、そのまま保険になる**

この退避が効くようにするため、**手順1（契約の再設計）を S-3 より先に置いている**。
