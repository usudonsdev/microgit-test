# ビルド検証エンジン 設計ドキュメント

最終更新: 2026-09-10（§15 マイルストーン計画を追加）

> **注記**: プロジェクト名は未決定。本文中では暫定的に「エンジン」と表記する。
> 命名確定後、インターフェース契約（§7）を固定する。

- ステータス: 計画段階（実装未着手）
- 関連プロジェクト: MicroGit（VS Code Marketplace 公開済み。設計は [design-policy.md](./design-policy.md)）
- 位置づけ: 卒業研究の実装対象。研究テーマ「mergeless branching」の一事例

---

## 1. 概要

マイクロコミット（保存のたびに自動生成されるコミット）単位でビルド可否を判定し、その結果を全件記録する常駐エンジン。記録された成否列を参照することで、原因コミット・原因位置の特定を、ビルドの再実行なしに行う。

判定を実用的な頻度で回すため、ビルドキャッシュを VCS のブランチ分岐に追従して Copy-on-Write で fork する。

---

## 2. 背景と問題設定

### 2.1 既存手段で成立しない理由

MicroGit は Ctrl+S ごとにマイクロコミットを生成する。1日あたり数百件。この粒度でビルド検証を回そうとすると、既存手段では頻度に耐えられない。

- `git worktree` + フルビルド: 作業ツリーのフル書き出し + ゼロからのビルド。1回あたり数十秒〜数分
- `tsc --watch` 等の watch mode: 高速だが履歴を持たない。「いつ壊れたか」を答えられない
- `git bisect`: 原因特定のたびに `O(log n)` 回のビルド実行が必要

### 2.2 着眼点

高頻度スナップショットが既に存在する環境では、ビルド検証結果を**悉皆記録**できる。悉皆記録が存在すれば、原因特定は探索問題ではなく走査問題になる。

この転換を成立させるための条件が、保存のたびの検証が現実的な速度で回ること。それを支えるのがブランチ追従型のビルドキャッシュ。

## 3. スコープ

### 3.1 研究対象（決定的・ローカル完結・LLM不使用）

- ビルドキャッシュのブランチ追従 fork
- ビルド成否の悉皆記録
- 原因コミットの特定
- 原因位置（単語単位）の特定
- エラーの存在区間の算出

### 3.2 プロダクトのみ（研究の評価対象外）

- LLM による「なぜこの差分がこのエラーを引き起こしたか」の説明生成
- pull 型（ユーザーが明示的に要求したときのみ実行）
- API キーは `vscode.SecretStorage` で管理

**設計制約**: エンジンは LLM なしで全機能が成立すること。

### 3.3 スコープ外

- Docker / Moby の丸ごと fork
- 自前の差分計算ロジック（再コンパイル範囲の判断）
- tip の常時グリーン化
- 独自の圧縮機構

## 4. システム構成

```
MicroGit（VS Code拡張・TypeScript）
    │  VCS層：マイクロコミット、マイクロブランチ管理
    │  → ブランチID、親ブランチID、コミットID、変更ファイル一覧
    ↓
エンジン（常駐デーモン・Go）
    │  キャッシュ管理層：cache/mb-N の用意、検証実行、結果記録
    │  → コンパイラ起動
    ↓
コンパイラ（tsc / cargo 等）
    │  再コンパイル範囲の判断、エラー位置の算出
    ↓
CI・デプロイ時クリーンビルド
       最終的な正しさを担保
```

**通信**: Unix ドメインソケット（Windows は名前付きパイプ）。保存のたびに叩かれるため、都度プロセス起動は避ける。

**言語選択**: エンジンを Go にするのは containerd snapshotter が Go ライブラリであるため。MicroGit（TypeScript）と同一プロセスに押し込むと、ここで無理が出る。

## 5. データモデル

### 5.1 マイクロコミット単位（1日数百件・全件記録）

| 項目 | 内容 | 備考 |
|---|---|---|
| ソース状態 | `views/<hash>` | MicroGit 既存機能。親view + 差分レイヤで復元 |
| ビルド成否 | 緑 / 赤 / 未検証 | 三値。未検証はデバウンス間引き・エンジン停止中を表す |
| エラー詳細 | file, 開始行・桁, 終了行・桁, code, message, 関連位置 | コンパイラの構造化出力をそのまま保持 |

コミットあたり数百バイト程度。全件保持しても負担にならない。

**保存先**: git notes または `.microgit_overlay/status/` のサイドカー JSON。

### 5.2 マイクロブランチ単位（1日数件）

| 項目 | 内容 |
|---|---|
| `cache/mb-N` | ビルドキャッシュ全体（`.tsbuildinfo`, `node_modules/.cache`, `target/`, `dist/` 等） |

分岐時に reflink（`COPYFILE_FICLONE`）で複製。同一ブランチ上ではコピーせずその場で再利用。

## 6. 機能要件

| ID | 機能 | 実現方式 | 探索 |
|---|---|---|---|
| F-01 | 保存時のビルド可否判定 | `cache/mb-N` 用意 → `tsc --noEmit` / `cargo check` | — |
| F-02 | 最後に緑だった地点への復元 | 成否列を後方走査 | 不要 |
| F-03 | 原因コミットの特定 | 緑→赤の境目を走査 | 不要 |
| F-04 | 原因位置の特定（単語単位） | 原因コミットの差分 ∩ コンパイラの span | 不要 |
| F-05 | エラーの存在区間の算出 | 同一エラーの連続区間を算出 | 不要 |
| F-06 | 修正パターンの索引 | 赤→緑の遷移点の差分を蓄積 | 不要 |
| F-07 | 未記録区間を跨ぐ場合の原因特定 | 当該区間のみ二分探索 | 必要 |
| F-08 | check緑・フルビルド赤の原因特定 | フルビルドで二分探索 | 必要 |

### 6.1 実行制御

保存イベントと検証実行を 1:1 で対応させない。デバウンス、実行中ジョブのキャンセル、最新のみ実行、アイドル検知を前提とする。

### 6.2 エラー同一性の判定

F-05 で必要。行番号は上部の編集でズレるため、行番号のみをキーにすると同一エラーが別物に見える。エラーコード + メッセージ + シンボル名を組み合わせて安定させる。

## 7. インターフェース契約

```
入力:
  branch_id        : string
  parent_branch_id : string
  commit_id        : string
  changed_files    : string[]

出力:
  status : "green" | "red" | "unverified"
  errors : [{
    file, start_line, start_col, end_line, end_col,
    code, message, related[]
  }]
```

この契約を満たせば MicroGit 以外の VCS やファイル監視ツールからも利用できる。契約は実装着手前に固定する。

## 8. 設計原則

1. **意味論は実装せず、基盤だけ提供する**
   再コンパイル範囲の判断はコンパイラ、圧縮は FS 層、CoW レイヤー管理は containerd snapshotter に委譲する。
2. **赤は信頼、緑は参考**
   差分検知漏れは「本当は壊れているのに緑」方向にしか働かない。非対称性を前提に設計する。
3. **分岐は常にブロックしない**
   赤からの分岐も許可する。mergeless の一貫性を保つ。
4. **粒度の分離**
   ソースはコミット単位で差分、ビルドキャッシュはブランチ単位で全体。
5. **LLM なしで全機能が成立する**

## 9. 設計判断の記録

### ADR-001: ビルド差分の判断をコンパイラに委譲する

- **決定**: エンジンは差分を計算しない。前回状態を用意し、再コンパイル範囲の判断はビルドツールに委ねる。
- **根拠**: エンジンが持つのは「このファイルが変わった」という情報のみ。`.d.ts` の型を1箇所変えれば下流の多数のファイルが再ビルド対象になるが、この推移閉包は `.tsbuildinfo` や cargo の fingerprint が持つ情報であり、ファイル差分から復元できない。自前実装すると「たまに古い成果物が残る」という検出困難なバグを生む。
- **副次的利点**: `--incremental` をサポートするツールであれば言語を問わず適用できる。言語ごとの依存グラフ解析を書く必要がない。
- **却下した代替案**: エンジン側で変更ファイル一覧から再コンパイル対象を決定する方式。

### ADR-002: キャッシュ粒度をブランチ単位にする

- **決定**: ビルドキャッシュはマイクロコミット単位ではなくマイクロブランチ単位で保持する。
- **根拠**: ソースツリーは数MB規模だがビルドキャッシュは `node_modules` 込みで数百MB〜GB規模。コミットは1日数百件生成されるため、この粒度で複製するとメタデータと GC が破綻する。ブランチは1日数件であり、数の桁が3つ違う。
- **却下した代替案**:
  - コミット単位での保持 → 上記の理由で破綻
  - 全ブランチ共通の単一キャッシュ（BuildKit / ccache 方式）→ ブランチ間を往復するたびに交互に上書きされ、切り替え頻度が高いほど効きが悪くなる。試行錯誤を主用途とする本ツールでは致命的

### ADR-003: 圧縮を実装しない

- **決定**: エンジンはキャッシュを圧縮しない。必要なら btrfs / zfs の透過圧縮に委ねる。
- **根拠**: gzip / zstd をかけると reflink のブロック共有が切れる。「分岐した瞬間ほぼゼロコスト」という前提が崩れ、複製のたびに実コピーと圧縮処理が走る。FS 層の透過圧縮は reflink より下のレイヤーで効くため、共有を維持したまま圧縮できる。

### ADR-004: Docker / Moby を fork せず containerd snapshotter を部品として使う

- **決定**: コンテナランタイム全体を fork せず、`containerd/snapshots` パッケージのみを利用する。
- **根拠**: Cursor が VSCode を fork できたのは、必要なものの大半がそのまま使えたため。Docker / Moby はネットワーキング、cgroup / namespace 分離、レジストリプロトコル、CLI、デーモン API が大半を占め、必要なのは CoW レイヤー管理部分のみ。fork すると upstream 追従義務（カーネル API 変更、セキュリティパッチ、containerd 互換性）が発生し、卒論スコープでは維持できない。
- **参照**: `Prepare(ctx, key, parent) ([]mount.Mount, error)` が本設計の fork 操作にそのまま対応する。overlayfs / btrfs / zfs / native の複数バックエンドに対応済み。
- **類例**: VSCode における Monaco Editor（製品全体を fork せず核だけを部品として使う）。

### ADR-005: 赤からの分岐を常に許可する

- **決定**: ビルドが失敗している状態からの分岐をブロックしない。
- **根拠**:
  - 「壊れたコードでも試行錯誤をそのまま残す」という MicroGit の前提と矛盾する。リファクタ中の中間状態は、その瞬間だけ見れば赤が正常
  - 「緑まで戻ってから分岐」を強制すると、進行中の作業が失われる。同じバグに対して複数の直し方を試す場合、起点は同じ赤になる
  - 「マージ前に緑必須」というゲートは合流点があるから機能する。mergeless 設計には合流点がないため、ゲートをかける自然な地点が存在しない
- **代替**: 分岐は常に許可し、キャッシュの信頼度のみ別軸で管理する。根元が赤 / 未検証の場合は複製時に「未検証」フラグを立て、次回ビルドで強制フルリビルドさせる。

### ADR-006: 赤は信頼し、緑は参考値として扱う

- **決定**: 原因特定は赤の情報のみを根拠とする。緑は判断基準として厳密に扱わない。
- **根拠**: 誤りの方向が非対称。インクリメンタルビルドの差分検知漏れは「本当は壊れているのに緑」方向にしか働かない。逆に「本当は正しいのに赤」はほぼ起きない（キャッシュ破損によるクラッシュは通常のコンパイルエラーと区別可能）。
- **補強**: `tsc --noEmit` / `cargo check` の緑はフルビルドの緑よりさらに弱い（リンクエラー、コード生成時エラーを検出しない）。最終的な正しさは CI / デプロイ時のクリーンビルドが担保するため、緑が完璧である必要はない。

### ADR-007: 原因特定は走査を主経路、二分探索をフォールバックとする

- **決定**: 記録済み成否列の後方走査を主経路とし、二分探索は限定的な状況でのみ実行する。
- **根拠**: `git bisect` が二分探索するのは中間コミットの成否が未知だから。本設計では全マイクロコミットに成否が記録済みのため、探索が不要。`O(log n)` 回のビルド実行が `O(n)` 回のメタデータ読み込みに置き換わる。
- **フォールバックが必要なケース**:
  1. 未記録区間（デバウンス間引き、エンジン停止中、GC 済み）を跨ぐ場合 → 当該区間のみ二分探索
  2. `check` は緑だがフルビルドが赤の場合 → フルビルドで二分探索

### ADR-008: エンジンを MicroGit から分離する

- **決定**: VS Code 拡張に機能追加せず、独立した常駐デーモンとして実装する。
- **根拠**:
  - 評価対象が明確になる。入力と出力が定義された単体としてベンチマークできる
  - MicroGit 依存を切れる。変更ファイル一覧を渡せる任意の VCS / 監視ツールから利用可能
  - 言語を分離できる。containerd snapshotter は Go ライブラリであり、TypeScript の拡張と同一プロセスに置くと無理が出る

### ADR-009: LLM をプロダクト機能に限定し、研究対象から外す

- **決定**: 原因コミット・原因位置の特定に LLM を使わない。LLM は「なぜこの差分がこのエラーを引き起こしたか」の説明生成にのみ用いる。
- **根拠**: エラー位置はコンパイラの span から、原因コミットは成否記録から、いずれも確定情報として取得できる。ここに LLM を挟むと、確定している答えを推測に置き換えることになる。
- **LLM が価値を持つ場合**: 原因コミットの差分とエラー位置が重ならないケース（型定義の変更が遠方のファイルでエラーを起こす等）。確定した2点を繋ぐ説明の生成は推論であり、LLM 向き。
- **運用制約**: 保存のたびに呼ぶとコストが破綻するため pull 型に限定。

### ADR-010: tip の常時グリーン化を目的にしない

- **決定**: プロダクト目標を「常にビルドが通る状態を維持する」とはしない。
- **根拠**: ADR-005 と矛盾するため。壊れた状態も記録し、赤からの分岐も許可する設計において、tip が常に緑である保証は原理的に作れない。
- **代替の目標記述**: 「どの分岐・どの時点についても、ビルド可能性の判定と復元を、保存の都度実行できるコストで提供する」

## 10. 先行研究・既存ツールとの関係

### 10.1 調査結果

| 領域 | 既存で解決済み | 空いている隙間 |
|---|---|---|
| ビルドキャッシュの永続化 | BuildKit `--mount=type=cache`, Bazel remote cache, ccache / sccache | ブランチ分岐への fork 追従 |
| 差分ビルド | 分割コンパイル（`.o` + リンカ、`target/deps/*.rlib`、`.tsbuildinfo`） | — |
| レイヤーの分岐 | Docker multi-stage build（共通 base から複数ターゲット） | 動的に生成される列への適用 |
| 本番エラーの原因特定 | Sentry Suspect Commits（スタックトレース → git blame） | ローカル・保存時点の粒度 |
| コードレビュー | CodeRabbit, Copilot code review 等（PR diff 対象） | 探索履歴・放棄された分岐 |
| 高頻度スナップショット | BranchFS (Fork/Explore/Commit, 2026-02), DeltaBox (2026-05) | スナップショットのビルド検証への応用 |

**要点**: BuildKit は ID / scope キー、Bazel と ccache はコンテンツアドレスで、いずれも VCS のブランチ構造を持たない。Sentry は本番デプロイ後、CodeRabbit は PR 時点であり、いずれもローカルの保存時点を対象としない。

### 10.2 新規性の位置づけ

**転用であり新規性を主張しない部分**

レイヤーキャッシュモデルそのもの。Docker / BuildKit が実証済み。「共通の接頭辞は使い回し、変更があった箇所以降だけ新しいレイヤーとして分岐する」という構造は同一。

**新規性A: VCS の動的分岐への CoW キャッシュ追従**

Dockerfile のステージは著者が事前に記述する静的な列。git の分岐は開発者がその場で生成する動的な列。キャッシュの fork / GC を git ref のライフサイクルに束縛する仕組みは、調査範囲で対応物がない。

**新規性B: 原因特定を探索問題から走査問題に退化させる**

`git bisect` は中間コミットの成否が未知であるため実行を伴う。Sentry は本番でエラーを検知してから blame を引く。いずれも「実行」または「事後照会」が必要。

高頻度スナップショットが既に存在する環境では、ビルド検証結果を悉皆記録できる。悉皆記録があれば、原因特定は探索を伴わない走査になる。

**A と B の関係**: B が結果、A が手段。悉皆記録を成立させるには保存のたびの検証が現実的な速度である必要があり、それを支えるのが A。A が成立する条件（分岐頻度とキャッシュサイズの境界）が実測対象となる。

**先行研究との配置**: BranchFS / DeltaBox は高頻度スナップショットを作るコスト自体を扱う。本研究はそれを所与とし、ビルド検証への応用側に立つ。競合ではなく上に乗る関係。

## 11. 評価計画

| ID | 測定内容 | 対応する主張 |
|---|---|---|
| E-01 | `git worktree` + フルビルド vs `views/` + `cache/mb-N` の所要時間 | 既存手段では頻度的に成立しないこと |
| E-02 | 分岐頻度を上げたとき、キャッシュ複製コストが利得を上回る点 | 新規性A |
| E-03 | 記録済み成否の走査 vs 実行を伴う二分探索の所要時間 | 新規性B |
| E-04 | ツール別の非対称性（tsc は型検査が支配的で、分割しても保存時に重い方を背負う） | 適用限界 |

E-02 が最重要。ここを測るまで `cache/mb-N` は定量的裏付けを持たない。

## 12. 既知リスク

| リスク | 内容 | 対策 |
|---|---|---|
| hardlink による破壊 | reflink 不可環境（NTFS 等）で hardlink にフォールバックすると、ビルドツールの in-place 書き換えで分岐元キャッシュが破壊される（SQLite ベースのキャッシュ、追記型で顕著） | reflink 不可ならフルコピー |
| 絶対パスの埋め込み | `.tsbuildinfo`、sourcemap がパスを保持するため、コミットごとにパスが変わると壊れるツールがある | 固定パスにマウント / リンクして見せる |
| キャッシュ肥大 | 分岐増加に伴いディスクを消費 | ref 削除に連動した GC。使用中キャッシュの可視化 |
| check の保証の弱さ | リンクエラー、コード生成時エラーを検出しない | ADR-006 の通り緑を参考値として扱う。最終防衛線は CI |
| エラー同一性の判定 | 行番号のみをキーにすると編集でズレる | code + message + シンボル名の組み合わせ |

## 14. MicroGit 側との接続点

本エンジンは MicroGit から分離した独立プロセスだが（ADR-008）、入力は MicroGit の VCS 層に依存する。既存設計との対応は以下。

| エンジンが必要とするもの | MicroGit 側の対応物 | 参照 |
|---|---|---|
| コミットID・変更ファイル一覧 | 保存イベントごとのマイクロコミット | [design-policy.md](./design-policy.md) §2 |
| ブランチID・親ブランチID | メインブランチ専属のマイクロ履歴空間 | [design-policy.md](./design-policy.md) §3 |
| ソース状態の復元（`views/<hash>`） | Node.js ユーザー空間 Overlay checkout | [NodeOverlay.md](./NodeOverlay.md) |
| 成否のサイドカー保存先 | `.microgit_overlay/` 配下 | [NodeOverlay.md](./NodeOverlay.md) |

本エンジンの要求が MicroGit 側の設計変更を伴う場合は、[design-policy.md](./design-policy.md) を先に更新してから本ドキュメントを追随させる（変更方向の正本は design-policy 側）。

## 15. マイルストーン計画（依存関係・リスク順）

研究では「ユーザーフィードバックを見ながら次の一手を決める」という意味でのアジャイルは機能しにくい。発表日という固定点があり、新規性A・B（§10.2）の主張が後戻りしにくいため。代わりに **「これが崩れたら設計全体が崩れる」前提を安いコストで先に検証し、成立を確認してから重い実装に進む**、リスク順の計画を採る。指導教員への進捗報告はこの表を単位とする。

### 15.1 クリティカルパス（優先して潰すべき前提）

エンジン設計全体は次の依存鎖の上に立つ。上流が崩れると下流の主張が成立しなくなる。

1. **reflink（または CoW 相当）による複製がほぼゼロコストで動く**（ADR-002〜004 の前提）
   崩れた場合: `cache/mb-N` の分岐複製は通常のコピーと同コストになり、ADR-002〜004 は成立しない。新規性Aは「Docker / BuildKit と同じことを遅く再実装した」に後退する。
2. **複製したキャッシュを、コンパイラが複製先のパスでも正しく再利用できる**（ADR-001 の前提、§12「絶対パスの埋め込み」リスク）
   崩れた場合: reflink 自体が高速でも `.tsbuildinfo` 等が旧パスを参照してキャッシュを再利用できず、結局フルリビルドが走る。①が生きていても②が死ねば同じ結論になる。
3. **①・②が両立した状態で、保存のたびの検証が実用速度（数秒未満）で回る**（新規性Bの前提＝悉皆記録の実現可能性）
   崩れた場合: デバウンス間引きが常態化し、F-07（未記録区間の二分探索）が例外ではなく主経路になる。「探索問題を走査問題に退化させる」という新規性Bの主張が成立しなくなる。

3つは独立に検証できるが ①→②→③ の順で依存する。**①・②の両方が崩れなければ③の見込みは立つが、③自体は①・②だけでは保証されない**（ツール側の型検査コストそのものが重い場合、E-04 の「非対称性」が残るため）。

### 15.3 このリストの使い方

M0〜M2 が失敗した場合（reflink が実用速度を出せない、または複製後の再利用性が崩れる場合）、卒論の軸を新規性Aから新規性Bのみに寄せる、または評価尺度を「fork コスト」から「検証頻度そのものの実用性」に置き換えるなど、スコープ変更の判断が必要になる。この判断は M2 完了時点で一度立ち止まって行う。
